# 이 저장소에 지침을 쓰는 규칙

## 어디에 쓰는가

| 내용 | 위치 |
| --- | --- |
| 한 스택(지침을 공유하는 묶음)에서 참인 규칙 | `rules/<스택>/` |
| 여러 프로젝트에서 쓸 절차 | `skills/<이름>/SKILL.md` |
| 여러 프로젝트에서 쓸 서브에이전트 | `agents/<이름>.md` |
| 여러 프로젝트에서 쓸 MCP 서버 | `mcp/<이름>/server.json`, `mcp/<이름>/README.md`. 값이 프로젝트마다 다르면 `README.md` 만 |
| 한 스택이 다른 스택의 절을 특정 환경에서 바꾸는 것 | 바꾸는 쪽 `rules/<스택>/README.md` 의 `## 다른 스택을 바꾸는 것` 표(→ 「다른 스택을 바꿀 때」) |
| 요소를 묶어 고르는 분류 | 각 요소 frontmatter 의 `categories`(→ 「분류」) |
| 스택을 들일 때나 클론마다 하는 세팅 | `rules/<스택>/SETUP.md`(→ 「세팅 문서」) |
| 한 프로젝트에서만 참인 규칙 | 여기 두지 않는다. 그 프로젝트의 지침 파일에 둔다 |

스택은 "언어" 가 아니라 **실제로 지침을 공유하는 단위**다. 자체 프레임워크 위에 올라간 묶음은 `java-spring` 이 아니라 그 묶음의 이름으로 짓는다. 어느 프로젝트에서나 참인 규칙도 그런 스택 하나(예: `base`)로 둔다. 도구는 어떤 스택도 특별 취급하지 않는다.

## 파일 규칙

- 파일 하나 = 주제 하나. 200줄을 넘기면 나눈다.
- 이름은 `NN-<주제>.md`. 주제는 소문자·숫자·`-`. 번호는 `00~99` 이고 그 스택 안에서의 순서만 정한다.
- 번호는 지침을 프로젝트에 넣을 때의 순서를 정하는 약속이다. `guideline list` 와 CLI 가 이 이름으로 지침 파일을 알아본다.
- 지침 파일에 **프로젝트 고유 명사를 쓰지 않는다.** 스크립트·패키지·클래스·컬럼·포트 이름이 들어가면 그 절은 더 좁은 스택으로 내려가거나 프로젝트에 남는다.
- 스택 파일은 그 스택의 **모든** 프로젝트에서 참인 것만 담는다. 프로젝트마다 다른 목록(암호화 컬럼 등)은 패턴만 남긴다.

## 칸 — 상시와 참조

지침 파일마다 맨 위 frontmatter 에 칸을 적는다. 프로젝트에 반영할 때 `always` 는 매 세션 읽히는 자리에, `reference` 는 따로 두고 색인에서 「언제 읽는가」 로 가리킨다.

```markdown
---
load: reference
when: "브라우저 MCP 서버가 안 붙거나, 워커에게 브라우저 확인을 맡길 때"
---

# 브라우저 서버가 안 붙을 때
```

- `load` 는 `always` 나 `reference` 이고 **필수**다.
- `when` 은 `reference` 에 **필수**이고 `always` 에는 쓰지 않는다. 「~할 때」 처럼 그 파일을 읽어야 하는 작업 시점을 쓴다. 주제 이름(「브라우저」)이 아니라 작업(「브라우저로 화면을 확인할 때」)으로 쓴다.
- 값은 한 줄로 쓰고, 값에 `: ` 가 있으면 큰따옴표로 감싼다(서브에이전트 frontmatter 와 같다).
- **분류 기준:** 그 규칙을 모르고 지나쳐 사고가 나는 순간이 아무 작업에서나 오면 `always`, 특정 작업을 할 때만 오면 `reference`.
- 한 파일 안에 `always` 절과 `reference` 절이 섞이면 파일을 나눈다. 칸은 파일 단위다.
- 스택의 파일이 전부 `reference` 여도 된다.

- **Why:** 칸이 없을 때 쓸 기본값을 두면, 분류를 빠뜨린 파일이 조용히 상시로 주입되어 모든 세션의 컨텍스트를 무겁게 한다.
- **How to apply:** 쓴 뒤 `guideline list <원본 폴더>` 의 `경고` 절에 그 파일이 없는지 본다. `스택` 절의 파일 옆에 칸과 `when` 이 나온다.

## 다른 스택을 바꿀 때

한 주제의 기본은 넓은 스택(예: `base`)이 갖는다. 특정 환경에서 그것을 바꾸는 것은 좁은 스택(예: `orca`)이고, 좁은 스택의 `README.md` 에 표로 선언한다.

```markdown
## 다른 스택을 바꾸는 것

| 이 스택의 절 | 바꾸는 절 |
| --- | --- |
| `05-switch.md` 「Orca 가 살아 있으면 워크트리도 Orca 로 만든다」 | `base/01-git.md` 「워크트리는 저장소 안에 만들고, 하나의 작업이 하나를 갖는다」 |
```

- 셀은 `` `<파일>` 「<## 절 제목>」 `` 이다. 이 스택 쪽은 파일 이름만, 바꾸는 절은 `<스택>/<파일>` 로 쓴다. 절 제목은 `## ` 뒤를 글자 그대로 옮긴다.
- 일부만 바꿔도 된다. 무엇을 대신하고 무엇은 따르는지는 바꾸는 절의 본문이 말한다.
- **넓은 스택은 좁은 스택을 가리키지 않는다.** 좁은 스택을 받지 않은 프로젝트에 없는 스택을 가리키는 글이 남는다.
- 같은 주제인데 환경 조건 없이 다르면 바꿈이 아니라 원본 안의 모순이다. 한쪽을 고친다.

**바꾸는 절은 `load: always` 파일에 둔다.**

- **Why:** 바뀌는 절이 상시에 있으면 에이전트는 그것을 매 턴 보는데, 바꾸는 절이 `reference` 에 있으면 읽을 계기가 없어 넓은 쪽을 따른다.
- **How to apply:** 바꾸는 절은 짧게 쓴다 — 전환 조건, 무엇을 대신하고 무엇은 따르는지, 절차가 있는 `reference` 파일. 쓴 뒤 `guideline list <원본 폴더>` 의 `경고` 에 그 README 가 없는지, 그 스택 아래에 `바꾼다` 줄이 나오는지 본다.

## 분류

내보내기 폼에서 요소를 분류로 한꺼번에 고르게 하려면 frontmatter 에 `categories` 를 단다.

```markdown
---
categories: [backend, spring]
---
```

| 요소 | 다는 곳 |
| --- | --- |
| 스택 | `rules/<스택>/README.md` frontmatter. 그 스택의 모든 지침 파일이 물려받는다 |
| 지침 파일 | 그 파일 frontmatter(`load` 옆). 스택 분류에 더해진다 |
| 스킬 | `skills/<이름>/SKILL.md` frontmatter |
| 서브에이전트 | `agents/<이름>.md` frontmatter |
| MCP 서버 | `mcp/<이름>/README.md` frontmatter. `server.json` 에는 쓰지 않는다 — 프로젝트에 그대로 옮겨진다 |

- 값은 한 줄 `[a, b]` 로 쓴다. 이름에 `,` 가 있으면 따옴표로 감싼다. 여러 줄 목록(`- a`)은 읽지 않는다.
- 대부분 스택에 달고, 스택 안에서 갈리는 파일에만 따로 단다.

- **Why:** 형식이 틀린 분류는 조용히 빠져서, 분류로 고를 때 그 요소가 빠진다.
- **How to apply:** 단 뒤 `guideline list <원본 폴더>` 의 이름 옆에 `[…]` 가 나오는지, `경고` 에 그 파일이 없는지 본다.

## 세팅 문서

스택을 프로젝트에 들일 때나 클론마다 해야 하는 세팅(설정 파일, 훅 설치, 환경 변수)은 지침 파일이 아니라 `rules/<스택>/SETUP.md` 에 쓴다. 상시로 읽히지 않고, 반영할 때 프로젝트의 `docs/guideline/<스택>/SETUP.md` 로 복사된다. 프로젝트의 관리 지침이 세팅할 때 이 문서를 읽게 한다.

```markdown
# <스택> 세팅

## 확인

<이미 세팅됐는지 가리는 법. 파일·명령>

## 세팅

1. <단계>
```

- frontmatter 를 두지 않는다.
- `SETUP.md` 와 `README.md` 만 있는 스택은 뼈대다. `guideline list` 에 나오지 않는다.
- 비밀값은 여기에도 두지 않는다. 환경 변수 이름과 발급 방법만 쓴다.

- **Why:** 한 번 하는 세팅 단계를 지침 파일에 쓰면 매 세션 컨텍스트에 실린다.
- **How to apply:** 쓴 뒤 `guideline list <원본 폴더>` 의 그 스택 줄에 `세팅 문서` 가 붙는지 본다.

## 절의 형식

```markdown
## <규칙을 한 문장으로>

<규칙 본문. 무엇을 한다/하지 않는다>

- **Why:** <어기면 무엇이 조용히 깨지는가>
- **How to apply:** <구체적인 행동. 명령이 있으면 코드 블록>
```

Why 를 지어내지 않는다. 근거를 모르면 올리는 것을 미룬다.

## 뼈대 스택

`rules/<스택>/` 에 `README.md` 만 있으면 뼈대다. `guideline list` 에 나오지 않는다. 첫 지침 파일(`NN-*.md`)을 넣는 순간 스택이 된다.

## 스킬

`skills/<이름>/SKILL.md` 에 둔다. frontmatter 는 `name`, `description` 두 개만 쓰고 값은 한 줄로 쓴다(에이전트마다 지원 필드가 다르다). `name` 은 디렉터리 이름과 같게 쓴다. 판단이 필요한 절차만 스킬로 쓴다.

## 서브에이전트

`agents/<이름>.md` 에 둔다. 하위 디렉터리는 두지 않는다. ruler 의 `.ruler/agents/` 원본 형식과 같아서 ruler 를 쓰는 프로젝트에는 그대로 들어간다.

```markdown
---
name: code-reviewer
description: 구현이 끝난 뒤 diff 를 읽기 전용으로 검토한다.
tools: [Read, Grep, Glob, Bash]
model: inherit
---

# Code Reviewer

<서브에이전트에게 주는 지시>
```

- frontmatter 는 `name`, `description`(필수), `tools`, `model`(선택)만 쓴다. `name`·`description` 값은 한 줄로 쓰고, 값에 `: ` 가 있으면 큰따옴표로 감싼다. 감싸지 않으면 YAML 이 읽지 못해 ruler 가 버리고 `guideline list` 도 무시한다.
- `name` 은 파일 이름과 같게 쓴다. 다르면 `guideline list` 가 무시한다.
- `description` 에는 언제 이 서브에이전트에게 맡기는지를 쓴다.
- `tools` 는 Claude 도구 이름(`Read`, `Grep`, `Bash` …)으로 쓴다. 다른 에이전트로는 반영할 때 옮긴다.

## MCP 서버

`mcp/<이름>/` 에 `server.json` 과 `README.md` 를 둔다. 서버 이름은 디렉터리 이름이다. 값이 프로젝트마다 달라 원본에 박을 수 없는 서버는 `server.json` 없이 `README.md` 만 둔다(→ 「반영할 때 항목을 만드는 서버」).

### 비밀값을 두지 않는다

토큰·비밀번호·API 키는 이 저장소에 두지 않는다. `${변수}` 참조로만 쓰고, 참조는 두 자리에만 쓴다.

- `env` 값: 키와 같은 이름의 참조 전체. `"DB_PASSWORD": "${DB_PASSWORD}"`
- `headers` 값: 참조 전체 `"${X}"`. `Authorization` 헤더만 `"Bearer ${X}"` 도 쓸 수 있다.

`command`, `args`, `url` 에는 참조도 토큰도 쓰지 않는다(쿼리 문자열 포함).

- **Why:** 이 저장소는 여러 프로젝트로 퍼진다. 그리고 Codex 는 `${…}` 를 펼치지 않아서, 위 두 자리의 참조만 Codex 의 `env_vars`·`bearer_token_env_var`·`env_http_headers` 로 옮길 수 있다.
- **How to apply:** 쓴 뒤 `guideline list <원본 폴더>` 의 `경고` 절에 그 서버가 없는지 본다. 비밀이 아닌 고정값(`LOG_LEVEL` 등)에도 경고가 뜨는데, 그런 값은 그대로 둔다.

### server.json

`.mcp.json` 의 `mcpServers` 항목 하나와 같은 모양이다.

```json
{ "type": "stdio", "command": "npx", "args": ["-y", "@upstash/context7-mcp"] }
```

```json
{
  "type": "http",
  "url": "https://gitlab.example.com/api/v4/mcp",
  "headers": { "Authorization": "Bearer ${GITLAB_TOKEN}" }
}
```

- `type` 은 `stdio` 나 `http` 이고 반드시 쓴다.
- stdio 는 `command`(필수)·`args`·`env`, http 는 `url`(필수)·`headers` 를 쓴다.

### README.md

- 무엇을 하는 서버인가, 어느 스택·어떤 프로젝트에 맞는가
- 필요한 환경 변수 각각과 발급·설정 방법

발급 방법을 지어내지 않는다. 모르면 올리는 것을 미룬다.

### 반영할 때 항목을 만드는 서버

`server.json` 을 두지 않고 `README.md` 의 `## 반영할 때 항목 만들기` 절에 항목을 만드는 방법을 쓴다. 반영하는 스킬이 그 절대로 대상 프로젝트에서 항목을 만든 뒤, `server.json` 이 있는 서버와 같은 방식으로 반영한다.

다음 두 가지를 모두 만족할 때만 쓴다.

- `url`·`command`·`args`, 또는 `env`·`headers` 의 비밀이 아닌 값이 프로젝트마다 다르다.
- 그 값을 프로젝트 안에서 알아낼 수 있다. 예: GitLab 호스트는 `git remote get-url origin` 에서.

토큰처럼 사람이 환경 변수로 넣어 주는 값이면 지금처럼 `server.json` 에 `${변수}` 로 쓴다.

`## 반영할 때 항목 만들기` 절에 쓸 것:

- 값을 어디서 읽는가(명령이나 파일)
- 어떻게 뽑는가. 읽은 값의 형태가 여럿이면(SSH·HTTPS 원격 주소 등) 각각
- 만들 항목의 모양. `server.json` 과 같은 필드로 쓰고, 채울 자리는 `<웹 주소>` 처럼 표시한다
- 사용자에게 묻는 지점. 값을 읽지 못함, 후보가 여럿(원격이 여럿 등), 뽑은 값이 이 서버에 맞는지 확신이 없음

```markdown
## 반영할 때 항목 만들기

1. 대상 프로젝트에서 `git remote get-url origin` 을 읽는다.
2. 웹 주소를 뽑는다. `https://` 로 시작하면 스킴·호스트·포트를 그대로 두고 사용자 정보(`…@`)와 경로만 뗀다 — 이 포트는 웹 포트다. `git@<호스트>:<경로>`·`ssh://` 형태면 `https://<호스트>` 로 쓴다 — 거기 붙은 포트는 SSH 포트라 뗀다.
3. 이 항목을 만든다: `{ "type": "http", "url": "<웹 주소>/api/v4/mcp" }`
4. `origin` 이 없거나, 원격이 여럿이거나, 호스트가 GitLab 이 아닌 것 같으면(github.com 등) 사용자에게 묻는다.
```

- 만든 항목에도 「비밀값을 두지 않는다」 가 그대로 적용된다. 읽은 값에 사용자 정보·토큰(`https://<사용자>:<토큰>@…`)이 있으면 떼고, 토큰을 읽어 항목에 넣는 절차를 쓰지 않는다.
- 절 제목은 글자 그대로 쓴다. `server.json` 도 이 절도 없으면 `server.json` 을 빠뜨린 것으로 보고 `guideline list` 가 무시한다. 절이 비어 있어도 무시한다.
- `server.json` 과 이 절을 함께 두지 않는다. 어느 쪽을 쓸지 모호해 `guideline list` 가 경고한다.

- **Why:** 한 프로젝트의 값을 원본에 박으면 다른 값을 쓰는 프로젝트에 틀린 값이 퍼진다. 이 절이 있어야 `server.json` 을 실수로 빠뜨린 것과 구별된다.
- **How to apply:** 쓴 뒤 `guideline list <원본 폴더>` 의 `MCP` 절에 `반영할 때 README 로 만든다` 로 나오는지 본다. `server.json` 이 없으니 `경고` 절의 비밀값 검사는 받지 못한다. 절에 적은 항목 모양에 비밀값이 없는지 직접 본다.

## 프로젝트에 닿기까지

수락하면 원본에 반영된다. 프로젝트에 닿는 것은 누군가 그 프로젝트에서 `guideline update`(또는 `guideline pick`)를 돌렸을 때다. 수락만으로 프로젝트에 반영됐다고 보고하지 않는다.

## 관리 지침 추가 문단

`docs/management.md` 는 이 원본에서 지침을 받는 **모든 프로젝트**의 관리 지침(`.ruler/guideline.md`)에 붙는 운영 규칙이다. 예: 「사내 지침은 보안 검토 후 제안한다」, 「배포 스택의 세팅은 인프라 담당자와 함께 한다」.

- 프로젝트의 관리 지침 끝에 `## <출처 이름> 추가 지침` 절로 붙는다. 이 원본에서 항목을 하나라도 받은 프로젝트에만 붙는다.
- `#` 제목은 쓰지 않고 `##` 부터 쓴다. 붙을 때 `##` 는 `###` 로 한 단계 내려간다.
- 고치면 각 프로젝트가 `guideline update` 로 받는다. 수정은 다른 원본 파일처럼 웹 편집이나 제안으로 한다.
