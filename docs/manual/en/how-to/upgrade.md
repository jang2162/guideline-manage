# Upgrade the server and the CLI

This guide upgrades the guideline server and the `guideline` CLI and lists the manual steps some versions need.
It is for server operators and CLI users moving to a newer release. What changed in each version is in [CHANGELOG.md](../../../../CHANGELOG.md).

## Upgrade the server

1. Check out the new release.

   ```bash
   git pull                    # or: git checkout v<version>
   ```

2. Rebuild and restart.

   ```bash
   docker compose up -d --build
   ```

The server upgrades the DB schema at startup.
Before it does, it writes `backups/guideline-pre-v<version>-<time>.db`, which is never deleted automatically.
If it does not start, see [Troubleshooting](../troubleshooting.md#the-server-does-not-start).

## Upgrade the CLI

```bash
npm install -g guideline-manage
```

- A server rejects a CLI older than 0.12.0 with "The CLI is too old — upgrade guideline-manage".
- Fetching from a public server without a token needs CLI 0.16 or later. The 0.15 CLI stops before asking the server when it has no token.
- **Upgrade the CLI and the server together to 0.24 or later** for the pick form: it chooses whole stacks and writes `guideline.json` version 3. A 0.24 server refuses an older CLI's form ("update the guideline CLI to 0.24.0 or newer"), and a 0.24 CLI skips a source whose server is older ("This server is older than the CLI", exit code 1). Updating, status and proposals do not need the server upgrade.
- `guideline pick --local` (the personal scope) and the **Required** marks of the pick form need a 0.24 server too. An older server does not know the personal form: `pick --local` cancels it with "This server does not know the personal form" (exit code 1).
- Commit `guideline.json` after the first `pick` or `update` with the new CLI. It is rewritten as version 3 (block keys); an older CLI cannot read it ("version is not 1 or 2").
- **Redeploy the server together with the CLI.** The pick form's script (`/static/selection.js`) is served by the server, and the 0.24 one files the leftover skills, subagents and MCP servers of `.guideline/` under the right step. An older server shows them under the wrong step.
- **Personal roles write version 2 files.** The first `guideline pick --local` (or `guideline role remove`) with a CLI newer than 0.24.0 writes `local.json` as version 2, and saving machine defaults writes `defaults.json` as version 2. A 0.24.0 CLI cannot read them: its `apply`, `update` and `status` compose from the project's choice only (`local-bad` to-do), and its `pick --local` stops with exit code 1. Upgrade the CLI in every worktree and on every machine that shares them. Version 1 files are still read.
- The role form (`pick --local --role`) works with a 0.24 server, which shows it as the plain personal form. Redeploy the server for the role's subtitle and the "project + my common selection get it" column.
- A 0.20 or later CLI works with an older server. `whoami` returns 404 there, so `guideline propose` sends proposals as before, and `status` and `login` show no token scope. An older CLI on a 0.20 server behaves as before.

## Move projects to the `.guideline/` layout

Since 0.24, received guidelines are copies in `.guideline/`, and the files ruler reads (`.ruler/<stack>/`, `.ruler/guideline.md`, `.ruler/ruler.toml`, `docs/guideline/`) are generated by `guideline apply` and git-ignored.
The first `guideline update` or `guideline pick` with a 0.24 or later CLI moves a project that was received in the old layout.
Until then `status`, `propose` and `apply` stop with "This project still uses the old layout" (exit code 2).

1. Upgrade the CLI of everyone who shares the project (`npm install -g guideline-manage`), and the server too.
2. Commit your work. The move rewrites tracked files and stops with "Commit or stash your changes first" when tracked files in the directory have uncommitted changes. Untracked files do not stop it.
3. In the project, run `guideline update` once. It needs the server. The move:
   - writes the received copies to `.guideline/` and keeps the edits the project made to them (they show as "edited in project");
   - moves overrides from `.ruler/<stack path>/` to `.guideline/overrides/<stack path>/`;
   - moves the settings of `.ruler/ruler.toml` into `.ruler/ruler.project.toml`, without the MCP tables that were received unchanged (an MCP table you changed stays and leaves an `mcp-conflict` to-do);
   - composes the generated files, writes the `.gitignore` block and removes the old copies, their indexes, the management guideline, `docs/guideline/README.md`, `ruler.toml` and the moved overrides from the git index (`git rm --cached`; the files stay on disk). A project file you added to a stack folder stays where it is, tracked;
   - rewrites `guideline.json` as version 3, which adds the rest of each chosen stack's files (`manifest-v3` to-do);
   - changes `prepare` in `package.json` from `ruler apply` to `guideline apply` when `guideline-manage` is a dependency and `ruler apply` has no arguments (with arguments you get a `prepare-manual` to-do and change it by hand).
4. Review `git status` and commit once: `.guideline/`, `guideline.json`, `guideline-lock.json`, `.ruler/ruler.project.toml`, `.gitignore`, `package.json` and the removed old copies.
5. Add the CLI to the project if you have a `package.json`, so that `prepare` can compose the files after a clone.

   ```bash
   pnpm add -D guideline-manage    # or: npm install -D, yarn add -D, bun add -d
   guideline apply                 # changes prepare from ruler apply to guideline apply
   ```

   Without `guideline-manage` as a dependency the CLI leaves `prepare` alone and gives a `dev-dependency` to-do with the command; `status` and `update` repeat it until you add it. Until then, `prepare` in a clone or a new worktree runs only ruler and writes an `AGENTS.md` without the guidelines. Without a `package.json` you get an `apply-hook` to-do: call `guideline apply` from your setup step (Orca: `scripts.setup` in `orca.yaml`).
6. Teammates pull, upgrade the CLI and run `guideline apply` (or `pnpm install` when `prepare` calls it). The generated files are not in git.
   - Pulling the move commit deletes the old generated files (`.ruler/<stack>/`, `.ruler/ruler.toml`, `docs/guideline/`) from their working tree, because git no longer tracks them. Run `guideline apply` right away. Do not run `ruler apply` alone before it: without `.ruler/ruler.toml` ruler writes files for every agent with nested off.
   - An unmerged branch that edited an old copy (`.ruler/<stack>/NN-*.md` or `docs/guideline/<stack>/…`) gets a modify/delete conflict when it merges the move. Put the edit in the copy at `.guideline/<id>` (for example `.guideline/rules/<stack>/NN-*.md`, which keeps the source's frontmatter; edit below it), then resolve the conflict by deleting the old path.
   - In a monorepo, `guideline apply` at the git root composes every committed unit below it too.

> [!WARNING]
> **Fix the `ruler` stack of your source.** If your guideline source has a stack that teaches ruler (for example `ruler`), it likely says `.ruler/` is the source, `ruler.toml` holds the settings and `prepare` runs `ruler apply`. That text lives on your server, not in this repository, and it is wrong for the new layout: say that `.guideline/` holds the received copies, that `.ruler/<stack>/`, `.ruler/guideline.md` and `ruler.toml` are generated, that ruler settings go in `.ruler/ruler.project.toml`, and that `prepare` runs `guideline apply`. Edit it on the web or send it with `guideline propose`.

## Update the seed on a running server

The `guideline-sync` and `guideline-export` skills and the authoring rules (`docs/authoring.md`) are a seed.
The server writes them only when it first starts on an empty DB.
A server that was started before the versions below keeps the old text, so update it by hand on the web.
`llms.txt` is rebuilt per request and changes right away.

> [!WARNING]
> **Servers started before 0.19:** add the "Recommend and receive" section to the `guideline-sync` skill and the "Required blocks" section to the authoring rules. Copy them from the same files under the language pack's `templates/`.

> [!WARNING]
> **Servers started before 0.20:** step 2 of the `guideline-export` skill says to use `--apply` only when the user asks to skip review. Rewrite it to say that with an `admin` token `guideline propose` applies directly and `--review` asks for a review. See the language pack's `templates/skills/guideline-export/SKILL.md`. Change the "send an edited copy upstream" row of `guideline-sync` the same way.

> [!WARNING]
> **Servers started before 0.21:** the `guideline-sync` skill does not handle the `missing-requires` to-do. In its "Handling to-dos" section, add `status` to the first line and add the `missing-requires` row. Copy them from the language pack's `templates/skills/guideline-sync/SKILL.md`.

> [!WARNING]
> **Servers started before 0.24:** the authoring rules have no "Child stacks" section, and the `guideline-sync` skill does not tell agents to choose child stacks by their `when`. On the web, copy these from the same files under the language pack's `templates/`.
>
> - Authoring rules: the "Child stacks" section, the child stack row in "Where things go", and the `<stack path>/<file>` cell and descendant warning in "Overriding another stack". Also the places a stack lands in a project (`.guideline/rules/<stack>/`, composed into `.ruler/<stack>/` and `docs/guideline/<stack>/`) in "Where things go", "Setup docs", "Display names", "Child stacks" and "Aliases".
> - `guideline-sync`: the child stack sentences in steps 1 and 2 of "Recommend and receive", and in "Handling to-dos" remove `new-file` from the `new-file`, `removed-upstream` row (the to-do no longer exists) and extend the `leftover` row.
> - `guideline-sync` for the `.guideline/` layout: the precondition about the old layout, the `guideline apply --json` row in "What to do", and in "Handling to-dos" the new kinds `apply`, `root-apply`, `unit-update`, `unit-problem`, `root-ruler-toml`, `no-copy`, `override-unchosen`, `mcp-conflict`, `untracked`, `stray-ruler-output`, `migrated`, `manifest-v3`, `prepare`, `prepare-manual`, `dev-dependency` and `apply-hook`. Remove `mcp-local`; the `mcp-build`, `subagents-off` and `nested-off` rows now name `.ruler/ruler.project.toml`; the `alias` row names `.guideline/overrides/<new name>/`; the Rules say not to edit `.guideline/` copies or the generated files.
> - `guideline-sync` for the personal scope: the precondition sentence about the personal form in monorepo subdirectories, the two personal rows in "What to do", the "Personal scope" section (`pick --local`, recommending with `{"add": …, "remove": …}` from the worker's own tools, Required blocks), the `scope: "personal"` paragraph under "Handling to-dos", the rows `setup-personal`, `personal-ignored`, `personal-shadowed`, `personal-revision`, `personal-sync`, `local-bad`, `ruler-leftover`, `override-target` and `unit-write-failed`, the `unit-update` and `unit-problem` rows that now name `update`, `pick` and `pick --local` at the git root, the personal sentence in the `removed-upstream` row, and the rule not to edit personal copies. The `setup-personal` row matters most: without it an agent sets up a personal stack like any other and may change committed files.
> - `guideline-export`: in step 1 and the example table, the places of the received copies (`.guideline/…`) and overrides (`.guideline/overrides/<stack path>/`), and `.ruler/ruler.project.toml` as the project's MCP settings.

> [!WARNING]
> **Servers started before 0.25:** the `guideline-sync` skill does not know personal roles. On the web, copy these from the language pack's `templates/skills/guideline-sync/SKILL.md`: the role row in "What to do", step 6 of "Personal scope" (`pick --local --role`, `guideline role use`), and the `role-missing` and `role-bad` rows in "Handling to-dos". Without them an agent does not know how to answer `role-missing` and `role-bad`.

> [!WARNING]
> **Servers started before 0.26:** the `guideline-sync` skill does not know `pick --recommend … --yes` (applying a recommendation without the form) or recommended removals in the project form. On the web, copy these from the language pack's `templates/skills/guideline-sync/SKILL.md`: the "Apply the recommendation without the form" row in "What to do", the `{"add": …, "remove": …}` sentences in steps 3 and 5 of "Recommend and receive", its step 6 (`--yes` only when the user said to apply without the form), and the `--yes` sentences in step 3 of "Personal scope". Without them an agent keeps opening the form, which is safe; with only part of them it may skip the form when the user did not ask for that.

> **Servers started before 0.27:** the `guideline-sync` skill does not know `guideline agents`. On the web, copy the coding-agent row in "What to do" and the `agents-mismatch` row in "Handling to-dos" from the language pack's `templates/skills/guideline-sync/SKILL.md`. Without them an agent may open the form to change agents, which cannot change them.
